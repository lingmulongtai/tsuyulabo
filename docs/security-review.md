## 運用上の互換性

- 新しい指紋は既存の `idempotency_keys.path` に収めた。スキーマ変更はない。旧版のレコードには本文の証拠がないため、24時間の保持期間中は409にする。操作結果を再照会してから再試行すること。特に通貨操作は、衝突エラーを見て無条件に新しいキーを発行しない。
- 旧版プロセスは指紋を比較しないため、新旧版の同時運用を避ける。将来、専用の `request_hash` カラムを追加する場合は移行手順を別途設計する。
- 再送の本文は同一バイト列が必要。JSONの空白・キー順の違いも別リクエストとして扱う。
- 本番では **APIとworkerの両方に `TSUYU_ENV=production` を明示する**。既定値はローカル開発用なので、自動的に本番と推定しない。32バイトは長さの下限であり、鍵は暗号学的乱数で生成して秘密管理サービスから配布する。
- しつけの星には発行後の待ち時間と通信時間を含む。ブラウザーの暫定表示と最終結果に差が出る場合がある。フレンド応答の削減と時計リセット制限も仕様に明記した。

## 推奨事項・残る検証

### Redis によるレート制限

今回の本文制限や冪等性は、毎回新しいキーを使う大量送信を制限しない。次を優先して導入する。

| 対象 | 制限単位と目的 |
| --- | --- |
| `/v1/auth/guest` | 接続元IP・ネットワーク単位。大量アカウントと初期300しずくの作成、DB書込みを抑制 |
| `/v1/shiori/ask` | ユーザー/IPの短期バースト、日次件数、推論費用、同時実行数。質問の言い換えによる費用増加を制限 |
| 個体の実験・行動・脳活動 | ユーザー/IPの計算量、実験のtrials合計、処理中ジョブ数。GETも対象 |
| パズル発行・提出、回路start/submit | ユーザー/IPの短期件数。未提出パズルの大量生成、失敗レコードと冪等キーの増殖を抑制 |
| フレンド追加・lab・like・gift | ユーザー/IP単位。コード探索、通知スパム、相互ロックの占有を抑制 |
| jobsのポーリング・home等 | ユーザー/IP単位。高頻度照会と遅延評価のDB負荷を抑制 |

Redis の原子的カウンターまたはトークンバケットで複数プロセス間の制限を共有する。429とRetry-After、信頼するプロキシのIP抽出、障害時の方針、上限と監視を定義する。入口でも本文・URL・ヘッダーサイズ、受信時間、同時接続数を制限する。上限値は利用頻度と実測費用から決める。

### 永続監査と配信

- 採集はバッグ状態の消費と台帳を原子的に更新するが、永続の独立した「採集受取イベント」はなく、台帳の参照はユーザーIDである。厳密に全報酬と個別イベントを一対一で追跡するには、受取ID・材料・経験値・対象個体を保存する経済イベントと台帳参照を追加したい。これは別途スキーマ設計・マイグレーションが必要で、今回の禁止範囲として実装していない。
- DBコミットからRedis enqueueまでの間にプロセスが停止するとジョブがpendingのまま残りうる。transactional outbox または定期的な未配信ジョブ回収が必要。冪等キーは外部キューの配送保証にはならない。
- 24時間以上の長期停止・再送に対して、TTLのある冪等キーだけでは改名やレベルアップ等の再実行を防げない。永続的な経済操作IDと監査・照合運用を検討する。
- 毎リクエストで行う期限切れキーの削除を定期バッチへ移し、ロック競合とテーブル増加を監視する。保存するゲスト応答にはBearerトークンが含まれるため、DB・バックアップとログのアクセスを制限する。

### 検証の限界

- 自動テストのDBはSQLite。並行操作はSQLiteのwriterロックでも直列化されるため、PostgreSQLの複数プロセスで、異なるキーの同時提出・相互ギフト・レベルアップ・残高移動・worker再配送を別途負荷試験する。
- 署名済みトークンの失効、鍵ローテーション、本番の外部IDプロバイダーへの移行は今回の対象外。
- 公開された盤面や操作記録から解を自動生成するボットは、サーバー検証だけでは区別できない。検証はルール・時計・所有権を保証するもので、人間が操作した証明ではない。
- 保存ジョブやDB自体を任意に改ざんできる攻撃者は本レビューの公開API境界の外側。実験再利用の所有者照合は防御を追加したが、全保存データの真正性を保証するものではない。
