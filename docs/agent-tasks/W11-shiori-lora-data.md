# Task W11-shiori-lora-data — training data and LoRA scripts for Shiori's own small model

Branch: `feat/shiori-lora-data`. Work in `services/shiori/` (dataset generator, tests, docs) and a new top-level
`ml/shiori-lora/` folder (training scripts). Do not change `services/api`, and do not add training libraries to the
uv workspace or `uv.lock` (CI must stay light).

## Why

The owner wants Shiori to run on a model we trained ourselves (企画書「11 AIを自分で作る」). W9/W10
(`services/shiori/reports/local-llm.md`) showed that off-the-shelf small models cannot keep Shiori's contract:
`qwen3.5:4b` got 33–64% count accuracy and dropped citations; `qwen3.5:2b-q4_K_M` was near 0%. The deterministic
`MockProvider` passes every gate (61/61) but only answers template questions. The plan is supervised fine-tuning
(QLoRA) of a small Qwen3.5 model on **ideal tool-use traces** generated by code, so the student learns: pick the right
tool and filters, copy `count` from `count_care_events`, put the number and its evidence ID in the same sentence,
separate observation / copy experiment / general research, and stay short.

The commander (Claude) will run the GPU training itself in WSL2 Ubuntu on this PC (RTX 4050, 6 GB VRAM) and import
the result into Ollama. Your job is to make that a few well-documented commands.

## What to build

1. **Oracle traces** (`tsuyu_shiori/dataset/`): a deterministic generator that builds synthetic weeks (reuse and extend
   `eval.synthesize` / `topic_questions` / the `open` questions; vary records, cues, days, sleep, scores, ranks, traits,
   associations and experiment outcomes by seed) and, for each question, the **ideal** conversation through the real
   tool layer (`tools.execute` on a `MemoryRecordStore` / `MemoryLab`):
   `system (agent SYSTEM_PROMPT) → user (same JSON payload run_agent sends) → assistant tool_calls → tool results →
   … → assistant final answer`. The oracle knows each question's parameters, so it calls the right tool with the right
   filters (e.g. `count_care_events(research_day=2, cue="apple_vinegar", valence="reward")`) instead of guessing.
   The final answer must pass `verify()` with zero dropped sentences and the eval's readability rules; reuse Mock's
   phrasing helpers where it helps, but add natural variation (several sentence patterns per intent) so the student
   does not just learn one template.
2. **Question variety**: several paraphrase templates per intent (counts by day/weekday/cue/valence, great success,
   preferences and 「なんで？」 with a copy experiment, sleep, cleaning, temperature, presentation rank, eclosion traits,
   pupation site, "no records" cases, general research via `search_papers`, and a few prompt-injection questions that
   must be answered safely). Hold some templates out of training entirely.
3. **Splits and export**: `python -m tsuyu_shiori.dataset --out data/shiori-sft/ ...` writes `train.jsonl`,
   `valid.jsonl`, `test.jsonl` (+ `stats.json`: counts per intent, token-length estimates, max length). Train seeds
   1000+, valid 2000+, and test = seed 37 (the eval's week) **plus** the held-out paraphrase templates. Each line is
   one example in the OpenAI-style chat format that Qwen's chat template / TRL accept: `{"messages": [...],
   "tools": [...]}`, with assistant `tool_calls` (`{"type":"function","function":{"name":…,"arguments":{…}}}`) and tool
   messages. Aim for ~4,000 train / 400 valid examples, each under ~3,000 tokens. `data/shiori-sft/` is git-ignored
   (add it); commit only the generator, tests and a small `services/shiori/reports/lora-dataset.md` with the stats.
4. **Tests** (`services/shiori/tests/`): every generated trace replays through `tools.execute` with identical results,
   every final answer verifies with zero dropped sentences, splits do not share seeds or held-out templates,
   generation is deterministic for a seed, and the JSONL validates against the format above.
5. **Training scripts** (`ml/shiori-lora/`, plain Python, Linux/WSL, not part of the uv workspace):
   - `requirements.txt` pinned for CUDA 12.x in WSL2: torch, transformers, peft, trl, bitsandbytes, accelerate,
     datasets (and `unsloth` as an optional faster path if it supports Qwen3.5). Check online which versions support
     Qwen3.5 (`Qwen/Qwen3.5-2B` and `Qwen/Qwen3.5-4B` on Hugging Face — verify the exact repo ids).
   - `train.py`: QLoRA SFT that fits 6 GB VRAM (4-bit base, LoRA r≈16 on attention+MLP, gradient checkpointing,
     batch 1 + accumulation, max length from `stats.json`, loss only on assistant turns). Args: `--base`, `--data`,
     `--out`, `--epochs`, `--max-steps`, `--lr`. Logs train/valid loss; saves the adapter.
   - `export.py` / `README.md`: the path to Ollama. Prefer `ollama create` with `FROM qwen3.5:2b-q4_K_M` + `ADAPTER`
     (safetensors LoRA) if Ollama supports adapters for this architecture; otherwise merge the adapter and convert to
     GGUF with llama.cpp (`convert_hf_to_gguf.py` + `llama-quantize Q4_K_M`). Include a `Modelfile` template that keeps
     the base model's chat/tool TEMPLATE and parameters (`ollama show qwen3.5:2b-q4_K_M --modelfile`). Name the model
     `tsuyu-shiori:2b-lora-v1`.
   - Write every command in `ml/shiori-lora/README.md` in order, from a fresh WSL2 Ubuntu (Python venv, CUDA check
     with `nvidia-smi` and `torch.cuda.is_available()`, Hugging Face download, train, export, `ollama create` on the
     Windows host, eval). You cannot run WSL or the GPU training from your sandbox: make the scripts correct, add a
     `--dry-run` that validates arguments and the dataset without loading a model, and say clearly what is untested.
6. **Eval hook**: the existing `python -m tsuyu_shiori.eval --provider ollama --qa-model <name>` must work for the
   trained model; add `--test-file data/shiori-sft/test.jsonl` (or similar) to also score the held-out paraphrases.

The host CPU cools poorly: keep tests fast and do not run live LLM evals in this task.
